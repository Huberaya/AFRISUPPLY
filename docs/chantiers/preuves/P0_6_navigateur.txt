P0.6 — PARCOURS DANS UN VRAI NAVIGATEUR : PREUVES
==================================================
Relevés du 2026-11-12. Navigateur réel (Chromium 153, sans affichage) piloté par
scripts/navigateur/parcours.mjs, contre :
  - le site CONSTRUIT (npm run build -w apps/web, servi tel quel — le même paquet JavaScript que celui
    que la plateforme d'hébergement sert en production) ;
  - une API réellement démarrée (npm run start -w apps/api), base PostgreSQL embarquée, e-mails écrits
    sur disque.

Ce que cela prouve : le site construit fonctionne dans un navigateur, de l'inscription à la
déconnexion, avec l'API du dépôt. Ce que cela ne prouve PAS : le site de production (autre base, autres
variables), ni la connexion par Clerk (service externe, injoignable depuis l'environnement de l'agent).
C'est la première validation par navigateur du projet : l'audit P0.1 n'en avait aucune.

Rejouer :
  npm run build -w apps/web && npm run start -w apps/api &
  (cd apps/web && API_URL=http://localhost:8787 npx vite preview --port 3100 --strictPort) &
  npm run verifs:navigateur
En intégration continue : tâche « Parcours dans un navigateur » (.github/workflows/ci.yml), avec le
Chrome de la machine ; le rapport et les captures d'écran sont joints à chaque exécution.


1. DÉFAUT TROUVÉ PAR CE PARCOURS — fenêtre « Nouveau fournisseur » hors de l'écran
--------------------------------------------------------------------------------------------
Constat (premier passage du parcours, avant correction) : sur un restaurant qui vient de s'inscrire,
le parcours n'a pas pu saisir le nom du fournisseur — le champ n'était pas cliquable.

Mesures dans le navigateur, écran de 1366 × 900, AVANT correction :

  A. Restaurant neuf (liste de fournisseurs vide)
     page animée   : transform = matrix(1, 0, 0, 1, 0, 0)   haut 198 → bas 278 (80 px de haut)
     voile         : haut 198 → bas 278, gauche 288 → droite 1334      ne couvre PAS l'écran
     fenêtre       : haut -167 → bas 643                               167 px au-dessus de l'écran
     champ « Nom du fournisseur » (obligatoire) : haut -62 → bas -24   HORS de l'écran, non cliquable

  B. Restaurant de démonstration (liste pleine)
     voile         : haut 198 → bas 810                                ne couvre pas l'écran
     fenêtre       : haut 99 → bas 909 ; champ : 204 → 242             visible

Cause : les pages de l'espace client ont une animation d'entrée qui se terminait sur
« transform: translateY(0) » et gardait cet état. Une transformation, même nulle, fait de l'élément le
repère de tout ce qui est en « position: fixed » à l'intérieur : les fenêtres de dialogue se plaçaient
donc par rapport à la PAGE et non à l'écran. Avec une page courte (un client qui démarre), le haut de la
fenêtre sortait de l'écran. Le défaut ne se voyait pas sur le compte de démonstration, dont les listes
sont longues — c'est le compte avec lequel l'application a été mise au point.

Portée : 13 écrans ouvrent une fenêtre de dialogue de cette façon ; 34 écrans portent l'animation.
Les tests existants ne pouvaient pas le voir : ils s'exécutent sans moteur de mise en page.

Correction :
  - apps/web/tailwind.config.js : l'animation se termine sur « transform: none » ;
  - apps/web/src/components/Modal.tsx : la fenêtre est rendue dans le document (portail), jamais dans
    la page qui l'ouvre.

Mesures APRÈS correction (identiques pour A et B) :
     voile   : haut 0 → bas 900, gauche 0 → droite 1366     couvre tout l'écran
     fenêtre : haut 45 → bas 855                             dans l'écran
     champ   : haut 150 → bas 188                            visible et cliquable

Captures : navigateur/fenetre-fournisseur-AVANT-restaurant-neuf.jpg, …-APRES-restaurant-neuf.jpg,
…-AVANT-restaurant-demo.jpg.
Garde-fous : le parcours mesure cette géométrie à chaque exécution (parcours 5) ;
apps/web/src/components/Modal.render.test.tsx (3 tests).


2. AUTRES CONSTATS DU PARCOURS
--------------------------------------------------------------------------------------------
  - Page de statut publique : la tâche « offsite-backup » s'affichait sous son nom technique, et le
    résultat des passages en anglais (« ok », « error »). Corrigé : libellés en français.
  - E-mail d'invitation : le rôle était écrit sous son nom technique (« staff »). Corrigé : « Équipe
    (quotidien) », comme dans l'application.
  - Page « Abonnement » sans paiement en ligne configuré : le client voit la liste des variables à
    renseigner (STRIPE_SECRET_KEY…). Comportement voulu et testé par le dépôt (transparence) ; relevé
    pour le dossier de commercialisation, non modifié.
  - Captures : les émoticônes ne s'affichent pas (police absente du navigateur d'essai) — sans rapport
    avec l'application.
